Data Types, scale and offset

Why this matters

  • Storage space!
  • Sentinel-2 bands are stored as raw integers (UInt16, values ~0–15000)
  • The conversion to surface reflectance requires a scale and offset — documented in a separate XML file
  • GDAL reads individual JP2 files, not the full product → the conversion is never applied automatically
  • To work with S2 data correctly, we need to understand what scale and offset are and how to apply them
  • ESA’s design assumes the full SAFE product is used with their toolchain (SNAP, Sen2Cor) — scale/offset lives at the product level (MTD_MSIL2A.xml), not the file level
  • GDAL reads files, not products — so there is no mechanism for it to auto-apply the conversion
  • This is the motivating problem for this entire section

Raster data types

  • Raster data is always stored as numeric
  • GDAL defines the supported types — shared by R, Python, QGIS
  • In memory: R/Python types; on disk: GDAL types
  • Choice of type affects file size and precision

Raster data types

  • If you store categorical data, use integer datatype and store the corespondence in the metadata
  • Always be minimalistic about which datatype you need.
  • Question if you have a continuous value from 0 to 1, which datatype do you use?
    • Not Float32! But Multiply by 100 and use Byte or by 1000 (if you need more precision) and use UInt16
  • Question: if you are measuring temperature, and your values are floating point ranging is -20 to +40 degrees, what datatype are you going to use?
    • Not CFloat32!
    • Multiply by 100 and use CInt16
  • Question: if you compute NDVI and have values in the range 0 - 1, what datatype do you use?
    • Not Float32, but not CInt16 either:
    • Transform the values to 0 - 255

  1. Difference in file size using constant dataset (same values and resolution) and varying the datatype

Choosing a data type

  • Naively: value range determines the datatype
  • Better: transform values to fit a smaller type
  • Example: NDVI ∈ [−1, 1] → rescale to [0, 255] → store as Byte

Rescaling / Transforming values

Min-max normalization maps any range \([\min(x), \max(x)]\) to a target range \([a, b]\):

\[x' = a + \frac{(x-\min(x))\times(b - a)}{\max(x)-\min(x)}\]

For NDVI ∈ [−1, 1] rescaled to [0, 255]:

  • \(x\) — measured value, \(x'\) — stored value
  • \(a = 0\), \(b = 255\) — target range
  • \(\min(x) = -1\), \(\max(x) = 1\)
  • We can use these values and simplify the formula as follows:

\[\begin{align} x' &= 0 + \frac{(x+1)\times 255}{2} \\ x' &= \frac{255x+255}{2} \\ x' &= 127.5x+127.5 \\ \end{align}\]

  • Formula: \(x' = 127.5x + 127.5\)
  • Example: NDVI \(0.2\) → stored as \(153\)
  • Two parameters describe the rescaling:
    • \(x' = x \times \underbrace{127.5}_{\text{scale}} + \underbrace{127.5}_{\text{offset}}\)

Precision (and lack thereof)

  • Only 255 distinct values → limited precision
  • Precision = \(\frac{1}{\text{scale}} = \frac{1}{127.5} \approx 0.008\)
  • Every stored NDVI is rounded to the nearest \(0.008\)
  • Is this enough? → depends on the use case

R Implementation for vectors

  • scale_minmax() applies the formula to a numeric vector:
scale_minmax <- function(
    x,
    a = 0,          # the minimum value of the new range (default 0)
    b = 255         # the maximum value of the new range (default 255)
    ){
  min_x = min(x)
  max_x = max(x)
  a + (x - min_x) * (b - a) / (max_x - min_x)
}
ndvi_measured <- runif(10, -1, 1)

ndvi_stored <- scale_minmax(ndvi_measured)

Restoring the original values

  • A colleague receiving your file needs to know how to get back the original values
  • Invert the transformation using scale and offset: \[x = \frac{x' - 127.5}{127.5}\]

R implementation for rasters

  • GDAL supports scale/offset natively (pass directly to writeRaster())
  • Values are stored in file metadata and recognized during import
  • Formulas to derive them from the value range:

\[\begin{align} \text{scale} &= \frac{b - a}{\max(x)-\min(x)} \\ \\ \text{offset} &= \frac{a \times \max(x) - b \times \min(x)}{\max(x)-\min(x)} \end{align}\]

Note:

  • \(a\) and \(b\) refer to the target range
  • min and max could either be the theoretical or practical extremes: What are pros / cons of using either?
scoff_params <- function(x, a = 0, b = 255, min_x = min(x), max_x = max(x)) {
  scale  <- (b - a) / (max_x - min_x)
  offset <- (a * max_x - b * min_x) / (max_x - min_x)
  c(scale = scale, offset = offset)
}

scoff_params(ndvi_measured)

scoff_params(ndvi_measured, min_x = -1, max_x = 1)

 127.5  127.5

R implementation for rasters

  • scoff_params() works for vectors, but needs two adjustments for rasters:
    1. min()/max() return per-cell values → use minmax() for global min/max
    2. writeRaster() divides by scale and subtracts offset → both must be inverted
scoff_params <- function(x, a = 0, b = 255) {
  stopifnot(nlyr(x) == 1)
  mm     <- minmax(x)[, 1]
  scale  <- (b - a) / (mm[2] - mm[1])
  offset <- (a * mm[2] - b * mm[1]) / (mm[2] - mm[1])
  c(scale = 1 / scale, offset = -offset)
}

R implementation for rasters

Let’s import a raster, calculate the scale and offset values and use these values to write to disk

elev <- rast(system.file("ex/elev.tif", package="terra"))

so <- scoff_params(elev)

writeRaster(
  elev,
  "data-out/datatypes/INT1U.tif",
  overwrite = TRUE,
  scale  = so["scale"],
  offset = so["offset"]
  )

R implementation for rasters

  • GDAL embeds scale and offset in the file metadata
  • On import, any GDAL-based software restores the original values automatically
  • The stored INT1U bytes are invisible — you always get back the original range

Lossless Compression

  • Even after choosing a compact datatype, files can be compressed further
  • Lossless compression reduces file size without changing any pixel values — the original data is perfectly recoverable
  • GeoTIFF supports several lossless algorithms via GDAL; DEFLATE is the most widely used
writeRaster(r, "output.tif", gdal = "COMPRESS=DEFLATE")
  • Compression is transparent to readers: any GDAL-based software (R, QGIS, Python) decompresses automatically on load
  • Combine datatype + compression for maximum savings: INT1U + DEFLATE can be 8× smaller than uncompressed FLT8S
  • DEFLATE is identical to the algorithm used in ZIP files — students will have intuition for it
  • LZW is an older alternative; ZSTD is newer and faster but less universally supported
  • Lossy compression (JPEG) exists for imagery but is rarely appropriate for analysis — pixel values change, which breaks indices and classification
  • “Transparent to readers” is the key selling point — no extra steps needed when loading the file

Out-of-range reflectance values

hist(s2b)
  • Reflectance is bounded by definition: 0 (no reflection) to 1 (perfect reflection)
  • Yet the histogram shows values both below 0 and above 1

Why are values out of range?

  • Below 0 — ESA intentionally introduced a −1000 DN offset (processing baseline 04.00)
    • Dark surfaces (deep water, shadows) can have slightly negative reflectance after atmospheric correction
    • The offset shifts all DNs up to keep them positive on disk; subtracting it back out exposes those negatives
    • These values are physically meaningful — clipping them to 0 alters real data
  • Above 1 — clouds and saturated pixels exceed the calibration reference; these are true artefacts
  • The proper fix for both is SCL masking: clouds (8, 9), shadows (3), and water (6) are flagged and excluded
  • After masking, residual out-of-range values are rare; clipping is then a safe fallback

Cloud Masking with the SCL Band

Why clouds are a problem

  • Clouds reflect strongly across all bands — a cloudy pixel does not represent the surface below
  • Using cloudy pixels in analysis (e.g. NDVI, classification) introduces severe errors
  • Sentinel-2 L2A includes a Scene Classification Layer (SCL) → per-pixel quality flag generated automatically during atmospheric correction
  • Unlike thin haze, which affects values subtly, clouds completely obscure the surface — affected pixels must be excluded, not corrected
  • The SCL is generated by Sen2Cor (ESA’s atmospheric correction processor) using spectral rules and auxiliary data
  • It is not perfect — thin cirrus and cloud shadows in complex terrain can be misclassified — but it is the standard starting point

The Scene Classification Layer (SCL)

Value Class Keep?
0 No Data ✗
1 Saturated / Defective ✗
2 Dark Area Pixels ✗
3 Cloud Shadows ✗
4 Vegetation ✓
5 Bare Soils ✓
6 Water ✓
7 Unclassified ~
8 Cloud, Medium Probability ✗
9 Cloud, High Probability ✗
10 Thin Cirrus ✗
11 Snow or Ice ✓
  • Class 7 (Unclassified) is ambiguous — in practice, many workflows discard it to be safe, others keep it
  • Classes 8 and 9 are the main cloud mask; class 3 (shadow) is equally important and often missed by users
  • Class 2 (dark area) catches topographic shadows in mountainous terrain — relevant in Swiss scenes

Importing the SCL band

  • The SCL band is stored as a separate JP2 file in the R20m resolution folder (not R10m)
  • It follows the same naming convention as the spectral bands
  • The SCL is only available at 20m and 60m resolution — it must be resampled to match the resolution of the band stack you are masking
  • resample(scl, s2b, method = "near") aligns it to the target grid — nearest-neighbour is correct here because SCL is categorical

Applying the cloud mask

# define which SCL classes are valid (cloud-free surface)
valid_classes <- c(4, 5, 6, 11)

# create a binary mask: TRUE where pixel is valid
cloud_mask <- scl %in% valid_classes

# apply to the reflectance stack
s2_masked <- mask(s2b, cloud_mask, maskvalues = FALSE)

# clip residual out-of-range values after masking
force_minmax <- \(x, min = 0, max = 1){ x[x < min] <- min; x[x > max] <- max; x }
s2_masked <- app(s2_masked, force_minmax)
  • %in% tests membership cell-by-cell and returns a Boolean raster
  • mask(..., maskvalues = FALSE) sets cells to NA wherever the mask is FALSE (i.e. cloudy)
  • Remind students that mask() was introduced in Lesson 1 — this is the same function, now applied for a real purpose
  • The result is a SpatRaster with the same bands as before but NA for all cloudy/shadowed pixels
  • Depending on cloud cover, this may remove a large portion of the image — this is expected, not an error

Valid pixels: 74.6%
  • If usable coverage is low, consider:
    • Choosing a different date with less cloud cover
    • Mosaicking multiple acquisitions from nearby dates
    • Seasonal compositing: combine all cloud-free pixels from a season into one image
  • A common rule of thumb: discard scenes with > 20% cloud cover over your study area
  • But study area cloud cover matters more than full scene cloud cover — a scene can be 80% cloudy globally but cloud-free over your area of interest
  • Seasonal composites (e.g. median of all July scenes) are very robust and widely used in land cover mapping
